## What shipped this session

1. **File-backed mmap A/C/B -> demand-paged B (v0.4.144/145/146, COMMITTED a60a12e).** Explored 3
   architectures (eager-client A, eager-server C, demand-paged B); kept B. mmap(MAP_SHARED/MAP_PRIVATE,
   fd, off) + msync/munmap write-back. New IPC: PIPE_MMAP_FILE(86)/PIPE_MSYNC(87)/PIPE_MUNMAP_FILE(88).
   Both fault handlers (exec_server + pipe_server) fill pages via vfs_pread (root vfs is inline, no nested
   seL4_Call; block reads are direct MMIO so safe in a fault handler). test_mmap app: 9/9 QEMU --smp 4.
   See [[project_mmap_file_plan]].

2. **Block-read hardening (v0.4.147, COMMITTED c784577).** virtio-blk completion poll captured used->idx
   AFTER QUEUE_NOTIFY -> raced QEMU host-RAM-fast completions under host scheduling jitter -> spurious -1 on
   UNCACHED reads -> exec ELF reads failed with spurious EPERM. Fix: blk_complete() captures `last` BEFORE
   notify (+ retry/re-notify belt-and-suspenders; the retry never fired -- the ordering was the cure).
   See [[feedback_virtio_blk_notify_race]].

3. **COW Step 3 RESOLVED (v0.4.148, uncommitted).** The "post-promotion fork+exec EPERM" (NEXT_20260503a)
   was NEVER a COW bug -- instrumented all of do_fork's return -1 sites, do_fork ALWAYS succeeded; the EPERM
   was the block-read race above (reproduced with COW gate OFF + on a clean build). With reads fixed,
   COW_STRIP_PARENT=1 works: 0 EPERM / 3 boots, parent_promotions 2, strip_errs 0, wc/head/grep/shutdown all
   run post-promotion. NEXT_20260503a's "trace do_fork -1 paths" plan was a wrong hypothesis.
   See [[project_cow_step3_finding]].

4. **RPi4 device-MMIO blocker FIXED + HW-VERIFIED (v0.4.149/150, uncommitted) -- the big one.** GENET +
   display were disabled in v0.4.98 for ONE shared root cause: seL4 device untypeds allocate FORWARD-ONLY
   from a watermark, and all RPi4 peripherals share one 64MB device untyped ([0xFC000000,0x100000000)), so
   MMIO must be claimed ASCENDING by paddr. GENET(0xFD580000) + VC mailbox(0xFE00B000) sit BELOW the
   first-mapped GPIO(0xFE200000)/UART(0xFE215000)/eMMC(0xFE340000) -> landed behind the watermark -> failed
   in _utspace_split_alloc. Fix: `prealloc_rpi4_devices()` (boot_device_map.c) maps ALL peripheral MMIO
   low->high in one pass right after DTB parse; the 4 drivers use the pre-mapped `dev_*_vaddr` globals.
   **VERIFIED on real RPi4:** [devmap] maps all 5 peripherals ascending -> non-null vaddrs, GENET responds
   `rev 0x06000000 (v6.0)`, eMMC works via the pre-mapped vaddr, ext2 mounts. See
   [[feedback_sel4_device_untyped_order]].

## GENET full bring-up (next deep effort, HARDWARE-GATED)

GENET MAPS and RESPONDS (rev v6.0) but the post-rev bring-up FAULTS -> kernel halt ("Kernel entry via
Unknown (0)"). Fault is the UMAC sub-block: UniMAC SW reset + MAC read at offset 0x808 (net_genet.c ~487-493).
The SYS block (rev, 0x0000) works but UMAC does NOT -- classic GENET clock-gating (MAC clock not enabled).
Made probe-only in v0.4.150 (`return -1` right after the rev print in plat_net_init -- remove that to
re-enable). To bring up: enable the GENET clock (CPRMAN / confirm firmware), fix UMAC reset sequencing, then
phy_init (BCM54213 MDIO), dma_init (128KB ring buf), ring_init (descriptors at GENET_DESC_BASE 0x10000 --
NOTE that's exactly at the 64KB/16-page map boundary; may need >16 pages), IRQ bind. Driver (net_genet.c,
741 lines) is otherwise ~complete. Each cycle = ninja build-rpi4 + mksdcard.py + flash + boot + serial
capture (slow). Agent estimate ~2-3 days.
