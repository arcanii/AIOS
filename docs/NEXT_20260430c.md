# AIOS Next Steps -- 2026-04-30c

Continuing from **v0.4.103**. On-demand mmap MAP_ANONYMOUS via IPC.

## Session Result: IPC-Based Anonymous mmap

### Goal
Provide a real demand-paged path for anonymous memory allocation, separate
from the eagerly-mapped static morecore BSS. Programs can now request
fresh pages from the kernel on demand instead of stealing from the
finite morecore_top pointer.

### Background
The static morecore_area is 6 MB (1536 pages) per process and is mapped
EAGERLY at ELF load by sel4utils_elf_load. mmap(MAP_ANONYMOUS) in
libsel4muslcsys default implementation just steals from morecore_top --
it doesn't actually allocate fresh pages. So a 4-process pipeline with
6 MB BSS each consumes ~6000 pages from the 8000-page pool.

True demand paging (don't pre-map BSS, fault-in on touch) requires deep
changes to the ELF loader and a custom fault handler. As a smaller
intermediate step, we now have a real anonymous mmap that requests
fresh frames from pipe_server (root) on demand. This unblocks programs
that need large allocations without forcing every process to pre-allocate
huge BSS.

### Changes

**New IPC: PIPE_MMAP_ANON (label 83)**
- `include/aios/root_shared.h`: defines PIPE_MMAP_ANON + PIPE_MUNMAP_ANON
- `src/servers/pipe_server.c`: handler allocates N pages via vspace_new_pages
  on caller's `proc.vspace`, returns vaddr in MR0
- Server-side headroom check via `vka_audit_check_headroom`
- Allocations counted in VKA_SUB_OTHER subsystem
- Cap: 1024 pages (4 MB) per call (caller can split larger requests)

**Client override: `aios_sys_mmap` in libaios_posix**
- `src/lib/posix_misc.c`: new `aios_sys_mmap` for `__NR_mmap`
- For `MAP_ANONYMOUS`: rounds up to pages, IPCs to pipe_ep, returns vaddr
- For non-anonymous (file-backed): returns -ENOSYS (not yet implemented)
- Replaces the default morecore-stealing impl from libsel4muslcsys
- Registered in aios_posix.c init

### Caveats / Next Steps

1. **Static morecore unchanged at 6 MB.** Reducing this requires
   verifying every program either fits in smaller heap OR uses mmap
   for large allocations. Done as a separate change after testing.

2. **No munmap implementation yet.** PIPE_MUNMAP_ANON label is reserved
   but the handler is not written. For now, mappings are reclaimed when
   the process exits (via sel4utils_destroy_process -> vspace_tear_down).

3. **No cap tracking per-process for mmap pages.** vspace_new_pages
   allocates frames AND maps them. The frames are tracked by the
   sel4utils vspace structure and freed at tear_down. We don't need to
   track them separately.

4. **File-backed mmap not implemented.** Returns -ENOSYS. This blocks
   some programs (memory-mapped files). Future work.

5. **mmap > 4 MB at once not allowed.** Per-call cap is 1024 pages.
   musl may need to be configured to split large allocations or we
   bump the limit. Most malloc implementations chunk into 4 MB anyway.

## Next Session Priorities

### Priority 1: Proper demand-paged BSS (real win)
- Patch sel4utils_elf_load (or write our own) to NOT pre-map BSS
- Add VM fault handler in root that allocates frames on access
- Result: per-process page count drops to ~10-30 pages for simple programs
- This is the architectural fix for the eager-allocation problem

### Priority 2: Reduce static morecore to test mmap fallback
- Drop CONFIG_LIB_SEL4_MUSLC_SYS_MORECORE_BYTES from 6MB to 1-2MB
- Programs that need more allocate via our new mmap IPC
- Verify TCC, zsh still work or document required configuration

### Priority 3: PIPE_MUNMAP_ANON
- Track mmap'd ranges per-process for explicit free
- Allows long-running programs to release memory

### Priority 4: file-backed mmap
- mmap of regular files (e.g., for executable mapping, large data files)
- Requires VFS read into newly allocated pages

### Priority 5: RPi4 hardware testing (deferred)
- Recovery mode banner is ready (v0.4.102)
- mkflash_rpi4.sh single-script flasher
