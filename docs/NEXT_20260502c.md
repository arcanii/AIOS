# NEXT 2026-05-02c: COW Phase 2 Step 3 -- kernel investigation

Read the seL4 AArch64 kernel page-map source before retrying parent-side
stripping. Captures answers to the three open questions from
NEXT_20260502b and proposes a minimal probe to confirm before writing
the real Step 3 in cow.c.

## Source references

All line numbers in `kernel/src/arch/arm/64/kernel/vspace.c`.

* `decodeARMFrameInvocation` (1506-1700) -- Map / Unmap dispatch
* `performPageInvocationMap` (1196-1211) -- the actual map
* `performPageInvocationUnmap` (1213-1230) + `unmapPage` (1035-1067)

## Q1: does seL4_ARM_Page_Map at the same vaddr in the same PD remap in place?

**Yes. No Unmap-first required.**

`decodeARMFrameInvocation` for `ARMPageMap` (1561-1583): if the cap
already has a valid mapped ASID, it accepts the invocation only when
both ASID and vaddr match the requested ones. So a same-PD same-vaddr
remap is the explicit allowed-remap path.

`performPageInvocationMap` (1196-1211):
```
bool_t tlbflush_required = pte_ptr_get_valid(ptSlot);
ctSlot->cap = cap;          /* overwrite cap in our slot */
*ptSlot = pte;              /* overwrite the PTE */
cleanByVA_PoU((vptr_t)ptSlot, pptr_to_paddr(ptSlot));
if (unlikely(tlbflush_required)) {
    invalidateTLBByASIDVA(asid, cap_frame_cap_get_capFMappedAddress(cap));
}
```

Three observable side-effects:

1. The cap stored in `ctSlot` (root-task cspace, where parent_cap lives)
   is overwritten with the new (re-)mapped cap.
2. The PTE in the target vspace at `va` is overwritten.
3. TLB for that ASID/VA is invalidated.

That is the *complete* set of touched state.

## Q2: what happens to the page-table entry when the cap's mapping rights are reduced?

**The PTE gets the masked rights. The cap retains its original VM rights.**

`decodeARMFrameInvocation` line 1531-1532:
```
vmRights = maskVMRights(cap_frame_cap_get_capFVMRights(cap),
                        rightsFromWord(getSyscallArg(1, buffer)));
```

The new PTE is built with `vmRights = min(cap_rights, requested_rights)`.

The cap struct itself only has its `capFMappedASID` and
`capFMappedAddress` updated (lines 1585-1586). VM rights stored in the
cap are **unchanged**. So a parent_cap with full rights, mapped R/O
via Page_Map, leaves the cap unrestricted -- a future Page_Map can
restore R/W without re-CNode_Copy.

## Q3: does the child's R/O dup interact with the parent's PD entry through the shared frame's CDT?

**No. The kernel's per-vspace state is independent.**

`performPageInvocationMap` only touches the cap slot you invoked on
(parent_cap's slot in root cspace) and the ptSlot in the target
vspace's page table. It does *not* walk the CDT, does *not* touch
sibling caps (the dup in child cspace), and does *not* touch any
page-table tree other than the requested vspace's.

Each vspace has its own page-table tree. Parent_pd and child_pd are
separate pte arrays. Updating parent_pd[va] does not update
child_pd[va]. The shared frame has one paddr that both PTEs point to,
but the PTE bits (rights, validity) are per-PTE.

Cross-checked `unmapPage` (1035-1067): it does the exact symmetric
thing -- looks up ptSlot in the target ASID's vspace and invalidates
that one PTE only. Even has a sanity check (1058-1061): if the PTE's
paddr does not match the cap's frame paddr, do nothing. So an
out-of-band remap that swapped the paddr would silently no-op an
Unmap on the original cap.

## So why did the previous attempt fail?

The failure was:
```
Caught cap fault in send phase at address 0xffffffffffffffff
in thread "child of: 'rootserver'" at address 0x46233c (arm_sys_send_recv)
```

The fault is the *child*, in `arm_sys_send_recv`, with cap = -1
(uninitialised). That is a *child* doing an IPC with a zero/garbage
cap. It is **not** a kernel-level page-map failure.

Per the kernel reading above, parent-side stripping cannot directly
corrupt the child's cspace or vspace. The most likely culprits are
the other things changed in the same commit:

* `cow_setup_stack` collided with the child's IPC buffer reservation
  (NEXT_20260502b explicitly notes this).
* The 1024-entry refcount table shifted BSS.

Either could have left the child running on garbage stack / IPC buffer
data, and its first syscall picked up an invalid cap pointer.

Conclusion: parent stripping in isolation is very likely safe. The
correct way to verify is a probe that does **only** the strip (no
stack COW, no refcount table at 1024 entries), and observes whether
the parent faults on the next write to a stripped page.

## Probe design

Add a `#define COW_PROBE_PARENT_STRIP 1` knob in cow.c. Gated:

In `cow_setup_segment`, after the successful `vspace_map_pages_at_vaddr`
of the child's R/O dup, also call:
```c
seL4_ARM_VMAttributes attrs = seL4_ARM_Default_VMAttributes;
seL4_CapRights_t ro = seL4_CapRights_new(0, 0, 1, 0);
int strip_err = seL4_ARM_Page_Map(parent_cap, parent_pd_cap, va, ro, attrs);
```

Do **nothing else**. No parent fault handling, no parent's
`cow_ranges` entry, no stack COW.

Expected outcomes:

1. **Strip silently succeeds, parent dies on first write to a
   stripped page.** Parent (dash) faults via VMFault. exec_thread or
   pipe_server fault handler logs the unhandled fault and treats it
   as exit. This is the success case for the kernel mechanism --
   confirms Page_Map remap works in production.
2. **Strip succeeds, no fault.** Either the parent never wrote to
   that page in the test session, or stripping silently no-op'd
   somewhere. Need to instrument or pick a forceably-written page.
3. **Strip returns error.** Capture errno, debug.
4. **Child crashes the way the previous attempt did.** That would
   contradict the kernel reading; investigate what we missed.

If outcome 1: implement Step 3 properly (parent's cow_ranges, parent
fault handling, refcount decrement on promotion).

If outcome 2-4: do not proceed; gather data and return here.

## Step 3 implementation sketch (after probe confirms outcome 1)

Pieces (all in cow.c):

1. **Track parent's range too.** In cow_setup_segment, after recording
   child's cow_ranges entry, also append the same [base, end) to
   parent's `active_proc_t->cow_ranges`. This is what gets the parent
   into the fault handler's purview.

2. **Strip parent in the per-page loop.** The Page_Map call from the
   probe, but check the err and rollback the dup-map on failure.

3. **Parent fault handling.** cow_handle_write_fault already keys on
   proc_idx; just wire it for any active_proc that has the faulting
   addr in its cow_ranges. The promotion path is identical:
   * Get current cap at va in faulter's vspace.
   * Capture paddr (for refcount release).
   * Allocate fresh frame, copy bytes.
   * Replace mapping R/W in faulter's vspace.
   * cow_frame_release(old_paddr).

4. **Refcount on parent strip.** Each strip is +1 acquire on parent's
   side. cow_frame_acquire is already wired into setup; just call it
   twice per page (once for child dup, once for parent strip).

5. **Parent dies safety.** Out of scope for Step 3. Note in cow.c that
   parent-dies-while-children-still-share is still broken; this is the
   Step 5 work.

## Test harness

Re-use `python3 /tmp/aios_drive.py`. After the probe lands, the smoke
should show either:
* parent (dash) dying with VMFault on the stripped data page (good --
  proceed to Step 3 implementation), or
* nothing visible (need a more forceful write).

If parent dies, the chain is: dash forks for `ls > /tmp/o`, parent
runs through `wait4`, writes to its own data segment (e.g., a global
fd table), faults. exec_thread sees the unhandled VMFault and treats
it as exit. The login session will hang. That is the diagnostic --
confirm and revert the probe.

## Probe results (v0.4.123)

Ran with `COW_PROBE_PARENT_STRIP 1`. **Outcome 1 confirmed.**

Smoke trace:
```
# echo SMOKE-START          <- builtin, no fork, fine
SMOKE-START
# ls /bin > /tmp/o          <- first fork
[INF] cow: cow_setup pages_shared=3   <- strip ran
wc -c /tm[INF] pipe: BSS lazy pages=1580
p/o
                            <- dash silently died here
AIOS login:                 <- getty respawned
```

Dash survived its first `fork+exec` for `ls` (the child ran and
exited). Dash died sometime after, before serving the next command
fully. exec_thread treated the VMFault as exit (no log line, no kernel
panic), getty respawned login.

The probe never logged a `strip_err`. /proc/cow's
`probe_strip_attempts` would have shown 3 per fork (segment had 3
shared pages). Couldn't read /proc/cow because the shell died.

What this rules out:
* Page_Map remap-in-place is not silently broken.
* It does not corrupt the child cspace/vspace (child `ls` ran).
* It does not crash the kernel.

What this confirms:
* The kernel does what the source said: parent's PTE is rewritten R/O,
  TLB invalidated, parent's next write to that page faults.
* The previous Phase 2 attempt's child cap-fault was caused by stack
  COW IPC-buffer collision or refcount-table BSS shift, NOT by the
  Page_Map call itself.

## Step 3 is unblocked

Implement as sketched above. The probe code can be left in cow.c with
the gate flipped off, or removed; either way Step 3 will write a more
complete version of the same call inline.

Order of operations for Step 3:

1. Extend `cow_setup_segment` signature with `parent_idx`. Caller
   (fork.c) passes it. We need it for parent's `cow_ranges` and for
   `parent->proc.pd.cptr` (cleaner than `vspace_get_root` though both
   work).
2. After successful child dup-map and `cow_frame_acquire`:
   * `seL4_ARM_Page_Map(parent_cap, parent_pd, va, R/O)`.
   * On error, undo the child dup-map (rollback). Otherwise:
   * Append `[base, end)` to parent's `cow_ranges` if not already present.
   * `cow_frame_acquire(paddr)` a second time -- parent now also shares.
3. Update `cow_handle_write_fault` to handle the parent case. The
   logic is identical (alloc fresh frame, copy bytes, replace mapping
   R/W, release old paddr). The only change is "which proc faulted"
   -- already passed in via `proc_idx`. Just make sure
   `cow_in_range / cow_find_range` work for the parent's slot too.
   (They already do; the function is purely table-driven.)
4. Smoke: `/proc/cow` should show non-zero promotions on the parent
   side; max_refcount should grow to 2-3 in pipe scenarios; no
   "BSS fault: map failed" regression vs v0.4.122.

Risks remaining (not addressed by Step 3):
* Parent dies before child promotes: child reads through the dup cap,
  but the underlying frame's cookie was held by parent's vspace. When
  parent's vspace tears down, the cookie gets freed even though the
  child cap still references it. This is the Step 5 problem.
* MAX_COW_RANGES is 4. With parent and child each tracking the same
  range, we may need to bump it. Or store parent ranges separately.

## v0.4.124 outcome -- Step 3 plumbing landed, strip gated off

All Step 3 plumbing is in place:
* `cow_setup_segment` takes `parent_idx`, has the strip path
* `cow_handle_write_fault` has the parent-promotion branch (kernel
  Page_Map of fresh frame, stash in `cow_promoted_global[]`,
  `cow_disabled_global[]` flag)
* `cow_release_proc` skips parent ranges (NULL reservation) for the
  vspace_unmap walk, frees `cow_promoted_global[]` entries
* fork.c passes `parent_idx`

Per-proc state (`cow_promoted_global[MAX_ACTIVE_PROCS][8]`,
`cow_num_promoted`, `cow_disabled_global`) lives in cow.c, NOT in
active_proc_t. First attempt put it in active_proc_t and the BSS
shift broke dash startup -- same lesson as the abandoned 1024-entry
refcount table. cow.c-local globals carry the same byte cost without
moving the active_procs layout.

Smoke (strip ON):
* getty boots fine, dash starts (first promotion = getty)
* `ls /bin > /tmp/o` runs, dash promotes during wait4
* `wc -c /tmp/o` produces no output -- but does fork. Investigation:
  fork.c falls back to `fork_copy_into_existing` when cow_setup
  returns -1 (cow_disabled), and that helper reads via
  `vspace_get_cap` which still points at the orphaned parent_cap. The
  child gets a snapshot of pre-promotion bytes, then exec'd into wc
  with that stale image. wc itself is fine; what's broken is dash's
  data passed across fork (job table, fd state, etc).

Smoke (strip OFF, current):
* BSS-fault count 11 (within v0.4.122 baseline of 10-12)
* /proc/cow shows `strip_attempts=0, parent_promotions=0`
* All v0.4.122 behaviour intact

## Follow-up to enable strip

One missing piece: `fork_copy_into_existing` must source from
`cow_promoted_global[parent_idx][i]` for vaddrs that have been
promoted, instead of from the cap returned by `vspace_get_cap`.

Sketch:
1. Add `uintptr_t cow_promoted_va[MAX_ACTIVE_PROCS][MAX_COW_PROMOTED]`
   alongside the cptr array (or fold into a struct). Set the va when
   stashing the fresh frame in `cow_handle_write_fault`.
2. Export `seL4_CPtr cow_current_cap(int proc_idx, uintptr_t va)`:
   * If `cow_disabled_global[proc_idx]` is 0, return `vspace_get_cap`.
   * Else iterate `cow_promoted_va[proc_idx]`; if matched, return
     the corresponding cptr.
   * Else return `vspace_get_cap` (page wasn't promoted).
3. In fork.c `fork_copy_into_existing`, take an `int parent_idx`
   parameter, and call `cow_current_cap(parent_idx, page)` instead
   of `vspace_get_cap(parent_vs, page)` for the source cap.
4. Flip `COW_STRIP_PARENT` to 1, smoke. wc/cat-pipes should work.
5. If they do, leave it on. If not, leave the gate off and dig into
   what else still reads stale parent data.

Estimated cost: ~30 LOC + smoke. Risk: low, because the gate flips it
on or off and we can land it disabled if the smoke regresses.
