# NEXT 2026-05-02b: COW Phase 2 attempt -- findings and a smaller plan

## Status

v0.4.120 was opened to land COW Phase 2 (parent-side stripping +
frame refcounting + stack COW per docs/DESIGN_COW_FORK.md) but was
abandoned mid-session and reverted. main stays at v0.4.119.

The work surfaced several findings worth recording before the next
attempt.

## What was tried

A new cow.c rewrite added:
* A `cow_frame_t` table keyed by frame paddr (from
  `seL4_ARM_Page_GetAddress`) with `cow_frame_acquire` /
  `cow_frame_release` helpers.
* `share_one_page` extracted from `cow_setup_segment` so both the
  data-segment and a new stack path could call it.
* Parent-side mapping stripped to R/O via direct
  `seL4_ARM_Page_Map(parent_cap, parent_pd, va, R/O)`.
* `cow_setup_stack` -- probe parent's stack range from sp downward
  and upward, share each mapped page, skip child's IPC buffer.
* WnR fault discrimination in `cow_handle_write_fault`: read fault
  on a R/O COW page = real fault, fall through to handle_child_fault.
* Parent's range added to its own `cow_ranges` so cow_release_proc
  walks parent's R/O-mapped pages on tear-down.
* `MAX_COW_RANGES` bumped 4 -> 8.

## What broke

### 1. Parent-side stripping caused cap-fault in forked child

After `seL4_ARM_Page_Map(parent_cap, parent_pd, va, R/O_rights)`, the
forked child crashed with:

```
seL4 ... Invocation of invalid cap #18446744073709551615
Caught cap fault in send phase at address 0
while trying to handle: cap fault in send phase at address 0xffffffffffffffff
in thread "child of: 'rootserver'" at address 0x46233c (arm_sys_send_recv)
```

The fault is a syscall on an invalid cap. The interaction is unclear
-- the parent's cap was unchanged, only the mapping rights were
modified. Possibly `seL4_ARM_Page_Map` at the same vaddr requires
unmap-first, or modifying parent's mapping affects the child's
page-table entry (since they share the underlying frame).

### 2. cow_setup_stack reservation collision

Parent's stack range often overlaps with child's IPC buffer
reservation. The probe walked from `parent_sp_page` outward until
hitting an unmapped page, but for getty the contiguous mapped range
was [0x10002000, 0x10012000) -- 16 pages around the IPC buffer area.
`vspace_reserve_range_at` in child failed because child's IPC buffer
lives at 0x10001000 in its own vspace.

Fix path: bound the probe more tightly (e.g., only walk
`THREAD_STACK_PAGES` pages around sp), or skip stacks entirely when
parent_sp is in the suspect low-memory range.

### 3. Refcount table size matters for BSS layout

The 1024-entry `cow_frame_t` table (~10 KB BSS) shifted the layout
in a way that re-introduced the `BSS fault: map failed` log noise
that v0.4.119 supposedly eliminated. Reducing to 64 entries (~640 B)
helped but didn't fully eliminate it.

**However**, post-investigation revealed: pure v0.4.119 ALSO has
~10 BSS faults per session in normal smoke tests. The v0.4.119 commit
message "eliminates the residual BSS fault noise" was overoptimistic
-- it reduced but did not zero out the noise. So this finding is
about long-standing behavior, not a Phase 2 regression.

### 4. MAX_COW_RANGES bump from 4 to 8 corresponded with broken pipe

When parent ranges were tracked AND `MAX_COW_RANGES=8`, `echo aaa | wc -c`
returned `wc: Operation not permitted`. Cause not pinned down before
revert. May be coincidence (BSS layout effects) or may be that parent
range tracking interferes with something in the IPC path.

## Plan for the next attempt

Make Phase 2 incremental. Each commit should be testable and
revertible on its own.

### Step 1 (small): WnR fault detection only
Add only: `(seL4_GetMR(seL4_VMFault_FSR) >> 6) & 1` check in
`cow_handle_write_fault`. Read fault on COW page returns 0 to caller
so it falls through to handle_child_fault. No new statics, no
behavior change for legitimate write faults.

### Step 2 (small): refcount table, observation-only
Add a small refcount table (e.g., 64 entries to limit BSS impact).
Wire `cow_frame_acquire` into `cow_setup_segment` and
`cow_frame_release` into `cow_release_proc`. Expose stats via
`/proc/cow` or extend `/proc/cachestats`. Behavior unchanged;
this is purely instrumentation. Verify against the v0.4.119 baseline
(which already has ~10 BSS faults per session) that the noise
count does NOT increase.

### Step 3 (medium): parent-side stripping
This is the most invasive piece and the one that broke last time.
Investigate first:
* Does `seL4_ARM_Page_Map` at the same vaddr in the same PD really
  remap-in-place, or does it require Unmap first?
* What happens to the page-table entry semantically when the cap's
  mapping rights are reduced?
* Does the child's R/O dup (mapped via `vspace_map_pages_at_vaddr`
  with R/O-rights cap) interact with parent's PD entry through the
  shared frame's CDT?

Try unmap-then-remap rather than direct Page_Map for stripping.
Verify that parent's writes after stripping actually trigger a
write fault.

### Step 4 (medium): stack COW
Bound the probe tightly. Skip when `parent_sp` is in low memory
(< 1 GB). Have `cow_setup_stack` call `cow_setup_segment` for the
single contiguous range it determines, rather than a separate code
path. This keeps the unified share_one_page path.

### Step 5 (large, deferred): parent-dies safety
Currently when parent dies, vspace_tear_down frees parent's
cookies, which invalidates child's CNode_Copy'd caps.
Mitigations:
* Zero parent's cookies for shared pages at fork time, track
  ownership in cow_frame_t, free in cow_frame_release when
  refcount hits 0.
* Or transfer ownership at parent reap.

Both touch sel4utils internals. Defer until the simpler pieces
are stable.
