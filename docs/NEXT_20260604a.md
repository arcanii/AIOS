## What shipped

1. **GENET MAC bring-up, HW-VERIFIED (v0.4.151).** The v0.4.150 "UMAC fault" was NOT
   clock-gating: the GENET powers up with SYS_RBUF_FLUSH_CTRL.SWINIT set, holding UMAC
   in reset; the first UMAC access (0x808) external-aborts -> kernel halt. Fix: write
   SYS_RBUF_FLUSH_CTRL=0 + delay before any UMAC access (Linux/Circle reset_umac order).
   On real RPi4: UMAC reachable, PHY BCM54213 (ID 0x600d:0x84a2) link up 100Mbps FD,
   boots to login. See [[genet-umac-swinit]].

2. **DHCP client (v0.4.152), QEMU-proven.** New src/net/net_dhcp.c: DISCOVER/OFFER/
   REQUEST/ACK at net_server startup, applies the lease to net_cfg_ip/gw/mask in place,
   falls back to static /etc/network.conf on a ~4s (CNTPCT-bound) timeout. net_stack
   hooks: accept broadcast / promiscuous while a lease is pending; route UDP port 68 to
   net_dhcp_input. On QEMU (`--net user`, SLIRP DHCP) it leases 10.0.2.15, then ARP+ping
   the gateway. See [[dhcp-client]].

3. **Tooling: aios_console.py.** configure_serial() crashed with termios EINVAL on this
   macOS host (killed the driver before reading -> `watch` never got a mirror); now falls
   back to `stty` on the open fd. Added `qemu --net user` (SLIRP + virtio-net w/ DHCP) --
   the fast QEMU net-dev harness.

## THE NEXT DEEP EFFORT: GENET DMA datapath (HARDWARE-GATED)

GENET MAC + PHY work, but the **descriptor DMA engines are inert in BOTH directions**, so
no frame is moved. This is why DHCP gets no reply on a real LAN.

**Evidence (v0.4.153 HW capture).** plat_net_driver_fn now POLLS the RX ring (the IRQ
path was never proven) and prints `RXp/RXc/TXp/TXc`:
```
[net-drv] RXp=0 RXc=0 TXp=1 TXc=0
[net-drv] RXp=0 RXc=0 TXp=4 TXc=0
[net-drv] RXp=0 RXc=0 TXp=6 TXc=0
```
- **TXp climbs (1->6)** = software queues frames (4 DHCP DISCOVER retries + grat-ARP +
  ARP request), but **TXc stays 0** = the TX DMA never consumes a descriptor -> nothing
  transmitted.
- **RXp stays 0** = RX DMA never produces.

**Already fixed in v0.4.153:** the RX producer index init was wrongly set to
GENET_RX_DESCS (16); it is HW-owned -> now initialized to 0 (Linux/Circle do the same).
The driver was switched from `seL4_Wait(IRQ)` to polling + diagnostics.

**Plan -- port the bcmgenet DMA-enable sequence** (Linux drivers/net/ethernet/broadcom/
genet/bcmgenet.c: bcmgenet_init_dma, bcmgenet_init_tx_ring/_rx_ring, bcmgenet_dma_enable):
1. **DMA_SCB_BURST_SIZE** (offset 0x0C from the DMA base) is never written -- set it
   (Linux uses DMA_MAX_BURST_LENGTH = 0x08).
2. **DMA_RING_CFG** -- the per-ring enable inside the DMA engine -- is never set. Linux
   writes `(1 << ring_index)` to TDMA/RDMA RING_CFG to activate the ring, in addition to
   DMA_CTRL (which we do set: DMA_EN | (1<<17) for ring 16).
3. **Ring START/END_ADDR units.** We write byte offsets (rx_desc_base = byte). Linux uses
   WORD-based descriptor addresses. Verify against the datasheet; the ring START/END_ADDR
   and READ/WRITE_PTR are WRITE-ONCE after a hard reset (RPi forum) -- write, then READ
   BACK and use the read-back value.
4. Re-check DMA_CTRL enable bit math and whether a global DMA enable / UMAC TX/RX-en
   ordering matters.
Then iterate: build-rpi4 -> mksdcard -> flash -> capture. A successful run shows TXc
climbing to TXp (TX sends), RXp advancing (RX receives), and **DHCP ACK with a real LAN
lease** (proves TX+RX end-to-end). Agent estimate: 1-3 focused HW cycles.

**Smaller GENET follow-ups (after DMA):** read the real board MAC via the firmware
mailbox (PROPTAG_GET_MAC_ADDRESS 0x00010003; vcmbox mapped -- fb_test.c mbox_call) instead
of the fake dc:a6:32:01:02:03 fallback; then switch RX back to IRQ-driven (unmask INTRL2_0
RX-done, the 0x200 block) once the datapath is proven.

- **QEMU net dev (FAST, no flashing):** `python3 scripts/aios_console.py qemu --kernel
  build-04/images/aios_root-image-arm-qemu-arm-virt --smp 4 --net user --shutdown

- **Serial capture (Pi off FIRST, else the tool grabs the leftover shell):** with the Pi
  OFF, `python3 scripts/aios_console.py serial /dev/cu.usbserial-0001 --login
  --cmd "sleep 18" --log /tmp/boot.log` (background), THEN power on. The `sleep 18` keeps
  the session connected past login so the async net_server DHCP/driver output is captured.
  `watch` in another terminal renders the live mirror.
