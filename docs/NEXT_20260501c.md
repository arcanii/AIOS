# NEXT 2026-05-01c: COW Fork Phase 1.5

## Status

v0.4.111: COW fork is now ENABLED for the file-backed (data) portion
of writable LOAD segments. The BSS portion still uses eager copy.
Functionality is preserved (pipelines, redirection, builtins all work
as before with COW gated off). The remaining concern is cosmetic:
sbase tools sometimes emit `BSS fault: map failed` /
`Range for vaddr X not reserved` log messages after fork+exec.

The same functional anomalies (`ls > /tmp/o` produces empty file,
`head -1` does not limit output) are observed BOTH with COW enabled
AND with COW gated off, so they are pre-existing bugs unrelated to
COW. They should be tracked separately.

## What changed in v0.4.111

* `src/process/cow.c`: `cow_setup_segment` now creates a fresh
  reservation (the elf_load reservation is freed by
  `sel4utils_elf_load`'s `clear_at_end` path -- discovered while
  debugging v0.4.110 -- so there is no overlap to worry about).
* New `cow_release_proc(int proc_idx)` explicitly unmaps the COW
  pages BEFORE `sel4utils_destroy_process`. This converts POPULATED
  entries (R/O dups) back to RESERVED, so when `vspace_tear_down`
  runs `sel4utils_free_reservation` on our COW reservation,
  `clear_entries_range` walks cleanly. Without this the v0.4.110
  abort-mid-walk leaked POPULATED entries and seemed to corrupt
  downstream vspaces.
* `cow_release_proc` is called from every destroy path:
  `pipe_server.c` PIPE_EXEC, `exec_server.c` exec_thread cleanup,
  `process/reap.c` reap_forked_child.
* `fork.c` step 6 bounds the COW range to `(vaddr, vaddr+filesz]`
  (page-rounded). The BSS portion `(filesz, memsz]` is left to the
  existing `fork_copy_into_existing` eager copy.
* `elf_seg_info_t` now carries `filesz` (set in both `exec_server.c`
  EXEC_RUN path and `pipe_server.c` PIPE_EXEC path).

Pages saved per fork (typical sbase tool, dash):
- COW: 3 data pages shared instead of copied
- BSS portion: still eagerly copied (~6 MB worth, but most pages
  unmapped via demand-BSS so only the ~handful parent has touched)

## Known cosmetic issue

After fork+exec runs, the freshly-execed sbase tool sometimes emits:

```
sel4utils_new_pages_at_vaddr@vspace.c:492
    Range for vaddr 0xXXXXXX with 1 4k pages not reserved!
[ERR] pipe: BSS fault: map failed err=18446744073709551615
```

The faulting process has a valid `bss_reservation` handle (verified
via logging: pointer, start, end all match what was set up in
`pipe_server.c` PIPE_EXEC). The reservation bounds include the fault
address. Yet `is_reserved_range` reports the entries as not RESERVED.

The errors fire only AFTER `cow_setup_segment` ran for an earlier
fork that involved the same parent binary (dash). Without COW,
errors do not fire. With COW + cow_release_proc + create-new
reservation: errors persist.

Hypotheses (from most to least likely):
1. **Memory aliasing.** A freed reservation_t / page-table tracking
   structure gets reused by ls's vspace via libc malloc, and some
   field is not properly reinitialized despite `perform_reservation`
   setting start/end/rights/cacheable. Need to log struct addresses
   to confirm.
2. **CDT side effects.** Our R/O dup caps are CDT children of
   parent's frame caps (rights reduced). When child A's vspace is
   torn down, kernel-level revocation of dup caps might somehow
   touch parent's frames or sibling frames. Less likely since CDT
   delete-vs-revoke distinction should keep parent untouched.
3. **kernel object reuse without zeroing.** vka allocates ls's PD
   from a freed UT that previously held child A's PD. seL4 Retype
   should zero the new object, but some internal state might
   persist. Worth checking PD allocation source.

The errors do not crash the system. Affected processes log the
error and exit (via handle_child_fault → reap). For pipelines, the
pipeline output appears correct (e.g., `echo aaa | wc -c` returns
`4`). Output redirection has a pre-existing bug (`ls > /tmp/o`
produces empty file with OR without COW).

## How to disable

If the BSS error log spam becomes problematic:

```c
/* in src/process/fork.c step 6, replace the cow_setup_segment block: */
cow_clear_proc(child_idx);
(void)cow_setup_segment;
for (int s = 0; s < parent->num_segs; s++) {
    elf_seg_info_t *seg = &parent->segs[s];
    if (!(seg->flags & 2)) continue;
    uintptr_t base = seg->vaddr & ~((uintptr_t)PAGE_SIZE - 1);
    uintptr_t end = seg->vaddr + seg->memsz;
    int np = (int)((end - base + PAGE_SIZE - 1) / PAGE_SIZE);
    for (int pi = 0; pi < np; pi++) {
        fork_copy_into_existing(&parent->proc.vspace, &cp->vspace,
                                base + (uintptr_t)pi * PAGE_SIZE);
    }
}
```

## Phase 2 outline (parent-side stripping)

Once Phase 1 is fully clean, Phase 2 should:
- Strip parent's mapping to R/O too (POSIX correctness: parent's
  writes should not leak into child until child writes its copy)
- Add refcounting for shared frames (so parent dying does not
  invalidate child's COW pages)
- Extend COW to stack pages (not just data segment)

These are documented in `docs/DESIGN_COW_FORK.md`.
