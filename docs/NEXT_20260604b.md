## TL;DR
GENET went from "DMA inert both directions" (v0.4.153) to FULL bidirectional networking
on real RPi4 hardware: cold-boot DHCP lease (192.168.0.8) + bidirectional ping (11/11,
0% loss, ~4.5ms), IRQ-driven RX, real board MAC (dc:a6:32:1c:2e:e1). All HW-verified.
Code committed this session (v0.4.154-162). The /proc/genet live probe was the key tool
-- it let us bisect the last bugs with live register pokes, zero flashes on the diagnosis.

## What shipped (v0.4.154 -> v0.4.162)
- v0.4.154 DMA register-map rewrite (vs U-Boot bcmgenet): descriptors in the register
  block (RX 0x2000 / TX 0x4000), ring regs 0x3000/0x5000, ctrl 0x3040/0x5040 (REG_OFF =
  desc_base + 256*12), word-unit ring addrs, DMA_SCB_BURST_SIZE + DMA_RING_CFG, DESC_OWN,
  TX QTAG+APPEND_CRC, RX prod/cons de-swap. TX started moving.
- v0.4.155 EXT_RGMII_OOB_CTRL config (RGMII mode/link + ID delay) -> RX started receiving.
- v0.4.156 /proc/genet live probe (dump/peek/poke/mr/mw/tx/reinit/ip/irqon/irqoff/mac).
- v0.4.157 DHCP xid reuse across retransmits (RFC 2131) -- a real-LAN OFFER landing in the
  next attempt window was rejected on xid mismatch (QEMU SLIRP replied instantly so it was
  masked). + IRQ instrumentation.
- v0.4.158 real board MAC via VC firmware mailbox + DHCP failure-mode counters + .ip
  one-line probe. First real-LAN lease.
- v0.4.159/160 RX IRQ-driven (live toggle) + ring-full deadlock fix (NAPI-style re-check
  of the producer before blocking).
- v0.4.161 UMAC_MAC1 16-bit byte-packing fix (was writing the reserved upper half ->
  unicast RX filter wrong -> broadcast worked but unicast/ping dropped).
- v0.4.162 RX IRQ-driven by default (unmask INTRL2 in plat_net_init). Cold-boot verified.

## Key lessons (recorded in [[genet-umac-swinit]])
- broadcast-works / unicast-fails == MAC RX filter wrong. Check UMAC_MAC0 (32-bit) /
  UMAC_MAC1 (16-bit field, bytes 4,5 in the LOW half) packing vs U-Boot/Linux.
- The RPi4 mini-UART drops chars on sustained output -> multi-line serial captures
  fragment. Design diagnostics as SHORT single-line probes (.ip and .mac survived).
- /proc/genet.poke confirmed fixes LIVE (poke.810.2ee1 -> ping worked) with zero flashes
  on the diagnosis itself. Build live diagnostics into the root task early.

## THE GOAL: control the Pi over the network, run it longer, flash less
The Pi is on the LAN at 192.168.0.8. Capability status for network control:

1. SSH -- WE HAVE A SERVER (src/ssh/, sshd_main.c). Listens on port **2222**, password
   auth (AES-256-CTR + HMAC, [[v0483 SSH auth]]/[[v0484 SSH channel]]), spawns /bin/dash.
   Run `sshd` on the Pi, then from a host: `ssh -p 2222 root@192.168.0.8`. It was built
   pre-GENET (tested over the older net path); FIRST TASK = confirm it over the real LAN
   GENET. Caveats: sshd is NOT auto-started (run it by hand); `listen(lfd, 1)` + single
   session -- likely serves one connection then needs re-running.
   NEXT: (a) confirm SSH over GENET; (b) auto-start sshd at boot (getty/init); (c)
   accept-loop so it serves repeated/multiple sessions. THIS is the immediate win for
   "claude controls the Pi over the network" -- no serial needed for commands.
2. REBOOT -- NOT IMPLEMENTED. aios_system_shutdown = seL4_DebugHalt (clean HALT only); no
   reset path. `shutdown -r` / `reboot` do not restart the board. ADD a real reset:
   BCM2711 watchdog (PM_RSTC 0xFE10_001C, PM_WDOG 0xFE10_0024, PM_PASSWORD 0x5A000000) or
   PSCI SYSTEM_RESET (0x84000009). Then `reboot` over SSH restarts without a physical
   power-cycle -- big for test iteration (run longer, fewer hands-on cycles).
3. SCP / SFTP -- NOT IMPLEMENTED. ssh_channel.c handles only "shell" requests (interactive
   dash); no "exec" channel and no sftp subsystem, so scp/sftp do not work. File transfer
   over SSH is unavailable. ADD an exec-channel + scp (sink/source) OR an sftp subsystem,
   OR a simple file-pull. Until then, move small files via the shell (base64 over SSH).
4. (Stretch) FLASH-OVER-NETWORK: scp a new kernel8.img to the FAT boot partition + reboot.
   Needs SCP + FAT-partition write + reboot. Removes the SD swap for code updates -- the
   real "flash less" endgame (a full image still needs the SD today).

Recommended order: confirm SSH over GENET (immediate) -> auto-start sshd + accept loop ->
reboot (watchdog) -> scp/sftp -> flash-over-network.

## Build / flash / test
- `ninja -C build-rpi4` -> `python3 scripts/mksdcard.py` -> disk/sdcard-rpi4.img ->
  balenaEtcher. Build BOTH build-04 + build-rpi4 after shared net code.
- /proc/genet live probe (RPi4 only; net_genet.c is rpi4-only): `cat /proc/genet` (full
  dump); `cat /proc/genet.ip` (one-line status: mac/ip/gw/bnd/rxp/irq/rep/off/ack/mis);
  `.peek.OFF` / `.poke.OFF.VAL`; `.mr.P.R` / `.mw.P.R.V` (MDIO); `.tx`; `.reinit`;
  `.irqon` / `.irqoff` (RX IRQ toggle); `.mac` (read real MAC via mailbox). All hex.
- Serial is the lossy mini-UART -- prefer short single-line commands; the boot
  `[net] DHCP result:` line + `.ip` survive. Capture:
  `python3 scripts/aios_console.py serial /dev/cu.usbserial-0001 --login --cmd "cat /proc/genet.ip"`.
  (After SSH-over-GENET is confirmed, drive the Pi over SSH instead -- far more reliable.)
- QEMU net harness still useful for shared net_stack/DHCP changes:
  `python3 scripts/aios_console.py qemu --kernel build-04/images/aios_root-image-arm-qemu-arm-virt --smp 4 --net user --shutdown`.
