# NEXT 2026-06-02 -- First RPi4 hardware boot (v0.4.135)

Outcome: AIOS booted on real Raspberry Pi 4 hardware for the first time
since v0.4.98. SMP did not come up; fell back to single-core (v0.4.135).
One real bug surfaced: shell pipes are broken on RPi4 (and only RPi4).

Read alongside HANDOVER.md and hw/rpi4/HARDWARE_TEST.md.

## TL;DR

* v0.4.134 (KernelMaxNumNodes=4) HANGS on real RPi4 at the
  firmware-to-kernel handoff: kernel8.img loads and relocates to
  0x80000, then the boot goes silent and never reaches "Bootstrapping
  kernel". The stall is the elfloader spin-table secondary-core
  bring-up.
* v0.4.135 = the documented fallback: KernelMaxNumNodes 4 -> 1 in
  settings-rpi4.cmake. Single-core boots cleanly to login on hardware.
* Works on HW: boot, login, eMMC/ext2, servers, /proc/hw,
  /proc/cmdline (platform-aware), file redirect, test_mprotect.
* BROKEN on HW: shell pipes. echo abc | wc -c -> "abc" + "0".
* Pipe bug isolated: NOT single-core, NOT the userspace binaries. It is
  RPi4-platform-specific. Top untested hypothesis: root-task morecore
  (8MB) shifting the root-task BSS layout on the RPi4 base address.

## 1. SMP hang on real hardware (v0.4.134)

Symptom (serial), v0.4.134 build 1691:

```
MESS: ... Loaded kernel8.img ... size 0x165440
MESS: ... Kernel relocated to 0x80000
MESS: ... Device tree loaded ...
MESS: ... uart: Baud rate change done...
<silence -- never reaches "Bootstrapping kernel">
```

Compare v0.4.98 (single-core, last known-good before this batch):
identical firmware sequence, then immediately "Bootstrapping kernel"
-> full boot. The only stage that runs between "Baud rate change done"
and "Bootstrapping kernel" and that differs between the two builds is
the elfloader spin-table secondary-core bring-up
(deps/seL4_tools/elfloader-tool/src/arch-arm/drivers/smp-spin-table.c),
which only runs when KernelMaxNumNodes > 1. The elfloader is silent on
this UART (no "Core N is up" prints ever reach serial, same as v0.4.98),
so the hang is invisible -- but it is parked in that bring-up loop.

Fix (v0.4.135): settings-rpi4.cmake KernelMaxNumNodes 4 -> 1.

To re-enable SMP later:
* First make the elfloader print on the RPi4 UART (bcm-uart.c) so the
  bring-up is visible at all.
* Then item E in docs/SEL4_DEVInvestigation.md: per-core boot trace to a
  fixed memory address, dumped by the boot core after a timeout, to see
  which secondary stalls and where. Likely a BCM2711 DTB
  cpu-release-addr / spin-table protocol mismatch.

## 2. First-boot functional results (v0.4.135, build 1693 on HW)

Works:
* Boot to login: eMMC/SDHCI SD driver, ext2 mount, crypto / serverstats
  / display / auth servers, warmup prefetch (19 files, 123559 bytes),
  getty, login root/root.
* /proc/hw: 4 cores (DTB enumeration -- NOT seL4 SMP), cortex-a72,
  3878 MB.
* /proc/cmdline: "platform=bcm2711 cpu=arm,cortex-a72 cores=4
  ram=3878M blk=emmc net=genet" -- v0.4.131 platform-aware /proc/cmdline
  confirmed on real silicon.
* File redirect: ls /bin > /tmp/o ; wc -c /tmp/o -> 608.
* test_mprotect: full MPROTECT-DONE (R/O, PROT_NONE, PROT_EXEC, munmap,
  re-mmap round trip) -- the v0.4.126-128 VM syscalls work on HW.

Broken:
* Shell pipes. echo abc | wc -c -> prints "abc" (writer output leaks to
  the tty) then "0" (reader got an empty stream).
  cat /etc/passwd | head -1 -> prints BOTH passwd lines (head got
  nothing). The pipe fd wiring in the forked children is not getting
  established. Every fork emits:
  ```
  sel4utils_new_pages_at_vaddr@vspace.c:492 Range for vaddr 0x458000/0x459000 with 1 4k pages not reserved!
  [ERR] pipe: BSS fault: map failed err=-1   (0xffffffffffffffff)
  ```

Cosmetic: the getty/login banner reads v0.4.134 (build 1692) because the
on-disk userspace (disk/disk_ext2.img) was not rebuilt -- only the
kernel + root task are v0.4.135. To unify: rebuild sbase + dash + zsh,
regenerate disk_ext2.img, reflash.

## 3. The pipe bug -- isolation experiment

Goal: is the pipe failure caused by the single-core fallback, or is it
RPi4-specific?

Method: build a single-core QEMU image identical to the qemu-virt config
except KernelMaxNumNodes, and run the same pipes.
* settings-smp1.cmake = copy of settings.cmake with KernelMaxNumNodes=1
  (needed because the FORCE in settings.cmake overrides a -D on the
  command line). Build dir build-smp1.
* MUST use -G Ninja. The Makefile generator breaks seL4's kernel header
  generation (syscall_header_gen.py: gen_headers/arch/api/syscall.h
  not found).

Results:
* QEMU single-core (build-smp1, same disk_ext2.img):
  echo abc | wc -c -> 4 ; cat /etc/passwd | head -1 -> 1 line ;
  seq 3 | wc -l -> 3.  PIPES WORK.
* Rebuilt build-smp1 with 8MB morecore (the RPi4 value): QEMU pipes
  still work. "BSS lazy pages" stayed 1580 because
  LibSel4MuslcSysMorecoreBytes only changes the root task + CPIO
  binaries, NOT the on-disk programs. dash/echo/wc come from
  disk_ext2.img and are byte-identical on QEMU and RPi4 (both report
  pipe BSS lazy pages = 1580).

Ruled out:

| Suspect | Verdict | Evidence |
|---|---|---|
| Single-core (MAX_NUM_NODES=1) | OUT | QEMU single-core pipes work |
| Userspace binaries / their morecore | OUT | identical disk_ext2.img, BSS 1580 on both |
| Root-task morecore alone (8MB) | OUT as *sole* cause | QEMU + 8MB root task pipes work |

Remaining (RPi4-platform-specific): the "Range for vaddr not reserved"
demand-BSS fault is BENIGN on QEMU (it prints, but the page is
effectively present and pipes still work) yet FATAL on RPi4 (the map
genuinely fails and the child breaks). This is
feedback_sel4utils_overlap_reservation.md manifesting on the RPi4
vspace/memory layout (RAM @ 0x0, 3878 MB) vs QEMU (RAM @ 0x40000000).

## 3.1 Hardware characterization (2026-06-02, via scripts/aios_console.py)

Drove the flashed v0.4.135 Pi over serial with the new driver (no
reflash, ~5 runs). This narrows the bug to the pipe path plus a leak, and
rules a lot out. Builtins work; forked exec works; ONLY pipes fail.

On the wedged Pi:
* echo HELLO (builtin) -> HELLO.                       (works)
* cat /proc/vka (forked /bin/cat, no pipe) -> prints,  (works) with
  benign "Range not reserved" noise during the fork. So fork+exec is FINE.
* echo x | wc -c -> "dash: Pipe call failed".          (pipe() fails)

Two behaviours, two linked bugs:

1. INTERMITTENT per-fork reservation failure (the trigger). On a fresh
   boot the same v0.4.135 card gives: echo abc | wc -c -> 4 (clean);
   seq 3 | wc -l -> 3 (with benign "Range not reserved" errors);
   $(seq 20) -> EMPTY (that fork failed outright). Non-deterministic per
   fork -> a race / allocation-order dependency in the demand-BSS
   reservation path (sel4utils overlap reservations), NOT a fixed config
   threshold. Signature: "Range for vaddr X not reserved -> map failed
   err=-1".

2. CUMULATIVE pipe-resource LEAK (the wedge). Each failed pipe leaks
   pipe_server resources: /proc/vka "pipe" pages climbed 2 -> 17 across
   the session (pipe: fr=17 pg=17, was fr=2 pg=2) while the VKA pool
   stayed healthy (live 772 of 8000). After ~4 runs EVERY pipe() returns
   "Pipe call failed" -- a pipe_server-internal slot/SHM exhaustion, NOT
   a VKA OOM. A fresh boot clears it.

So bug 1 (reservation race) faults a pipe child; bug 2 (pipe_server does
not release the half-built pipe when its fork faults) leaks the slot/SHM,
and enough leaks wedge pipe() permanently.

NOT memory pressure: /proc/vka live 772/8000; /proc/meminfo PoolFree
~29 MB; /proc/cow observe-only (table_live 0).

Fix fronts -- bug 2 FIRST (higher impact: turns "wedges forever" into
"intermittent but self-healing"):
* pipe_server: on a child fork fault / abnormal exit, free the pipe
  (slot, SHM region, caps). Start at the "Pipe call failed" allocation
  path + the fork-fault handler in src/servers/pipe_server.c; confirm the
  leak with /proc/vka "pipe: pg" before/after a forced failure.
* demand-BSS reservation race (bug 1): src/servers/pipe_server.c +
  exec_server.c fault dispatch; on the failing vspace_new_pages_at_vaddr
  try a direct seL4_ARM_Page_Map to learn whether the page is genuinely
  unmapped (kernel) or just mis-tracked (libsel4utils) -- see item D
  (seL4_DebugDumpPTE) in docs/SEL4_DEVInvestigation.md.

Measure via the driver (fresh boot each time -- the wedge is sticky):
  scripts/aios_console.py serial /dev/cu.usbserial-0001 --login \
    --cmd 'echo abc | wc -c'   (repeat; watch /proc/vka "pipe: pg" grow)

## 3.2 Fix design

DONE in v0.4.138 (safe, no new state): pipe_maybe_free now calls
vka_audit_frame_release(1) for each freed pipe frame (shm + xfer), so the
global "live" page counter in /proc/vka is accurate after pipe frees.
PIPE_CREATE / PIPE_MAP_SHM bump live via vka_audit_frame but the free
path never decremented it, so "live" inflated by one per pipe freed --
useless as a leak gauge. Now it tracks real live pages: watch /proc/vka
"live" across a pipe loop on the Pi to measure the actual leak.

NOT DONE -- the wedge cure (needs new state + hardware testing):

The wedge: MAX_PIPES = 16 (root_shared.h). Each leaked pipe keeps its
slot (active=1) and SHM page; after ~16 leaks PIPE_CREATE finds no free
slot and returns -1 -> dash prints "Pipe call failed". A pipe leaks when
its refs never both reach 0 (intermittent fork failure unbalances the ref
accounting), so pipe_maybe_free never runs.

Safe reclaim design (recommended): on PIPE_CREATE finding no free slot,
reclaim genuinely-orphaned pipes before returning -1, then retry the slot
scan. A pipe is safe to reclaim iff:
  * had_child == 1 (it was ever associated with an exec'd child), AND
  * no active_proc references it (no stdout_pipe_id/stdin_pipe_id == pi),
    AND
  * no blocked reader is waiting on it.
The had_child guard is ESSENTIAL: it protects a freshly-created pipe the
shell has not yet exec'd children into (refs 1/1, no reference yet) --
without it the reclaim could free an in-flight pipe. Set had_child=1 at
the exec association (pipe_server.c ~line 986/989), clear it at CREATE.
Reclaim = reset refs to 0 + pipe_maybe_free(pi). This makes the system
self-healing ("wedges forever" -> "intermittent but recovers") without
having to perfectly balance the refs.

CAVEAT -- BSS shift: had_child is one bool per pipe. Do NOT add a field
to pipe_t in root_shared.h (array pipes[MAX_PIPES]) -- that shifts the
root-task BSS, and this codebase is documented-fragile to that
(v0.4.118 stack overflow; v0.4.122/124 BSS shift broke dash). Use a
separate `static unsigned char pipe_had_child[MAX_PIPES];` in
pipe_server.c (16 bytes) and test on hardware after. This is why it was
deferred from v0.4.138 -- it must be verified on the Pi, the only place
the bug reproduces.

Optional deeper fix (bug 1, the trigger): the demand-BSS reservation
race itself. On the failing vspace_new_pages_at_vaddr, try a direct
seL4_ARM_Page_Map of a fresh frame at the faulting vaddr; success means
libsel4utils only mis-tracked it (a retry could mask the race), failure
means the kernel genuinely has no mapping. seL4_DebugDumpPTE (item D,
SEL4_DEVInvestigation.md) answers this directly.

Verify any fix with the driver (fresh boot -- the wedge is sticky):
  scripts/aios_console.py serial /dev/cu.usbserial-0001 --login \
    --cmd 'echo abc | wc -c'   (x20-30); pipes should stay working and
  /proc/vka "live" should not climb.

## 4. Pipe bug -- next session (cheapest first)

1. RPi4 at 6MB morecore. The root task is 8MB on RPi4 vs 6MB on QEMU.
   8MB alone does not break QEMU pipes, but 8MB on the RPi4 base address
   shifts the root-task BSS layout, and this codebase is documented-
   fragile to root-task BSS shifts (v0.4.118 stack overflow that looked
   like a BSS bug; v0.4.122/124 BSS-shift broke dash startup). Test: set
   LibSel4MuslcSysMorecoreBytes 6291456 in settings-rpi4.cmake, rebuild
   build-rpi4, reflash (hash gate!), check pipes. If 6MB fixes it ->
   quick win, and the open question becomes "why is the layout fragile."
2. Instrument the BSS fault handler. In src/servers/pipe_server.c
   (forked-child fault dispatch) and src/servers/exec_server.c
   (exec_thread loop), on the failing vspace_new_pages_at_vaddr try a
   direct seL4_ARM_Page_Map of a fresh frame at the faulting vaddr
   (bypassing libsel4utils reservation tracking). Direct map succeeds ->
   bug is purely libsel4utils bookkeeping. Direct map fails -> deeper
   (kernel PT state / paddr).
3. seL4_DebugDumpPTE (item D, docs/SEL4_DEVInvestigation.md): answers
   "is the page actually mapped at this vaddr?" definitively --
   distinguishes the benign tracking error (QEMU) from a genuine
   unmapped page (RPi4).
4. Dump the reservation list for a forked child on RPi4 vs QEMU
   (v0.4.106 demand-BSS: vspace_unmap_pages + vspace_reserve_range_at,
   stored as bss_reservation in active_proc_t) and look for the overlap
   the feedback note describes.

Files: src/servers/pipe_server.c, src/servers/exec_server.c,
docs/DESIGN_DEMAND_BSS.md, feedback_sel4utils_overlap_reservation.md,
include/aios/root_shared.h (active_proc_t: bss_lazy_start/end,
bss_reservation).

Tooling: scripts/aios_console.py (v0.4.137) drives a running AIOS over a
qemu unix socket or the Pi serial (/dev/cu.usbserial-0001) with no pty --
use it to script the repro loop (boot -> login -> run -> read) instead of

## 5. Hardware flashing workflow (macOS) -- learnings

Flashing was the hard part this session. For future hardware sessions:

* The Mac built-in SDXC reader reports `Device Location: Internal`, so
  scripts/flash-rpi4.sh REFUSES it -- the internal-disk guard is a false
  positive for built-in readers. The card was /dev/disk6, "Built In
  SDXC Reader", Protocol Secure Digital, Removable: Removable, Media
  Read-Only: No -- safe to write.
* CLI dd is blocked three ways on current macOS:
  - sudo "unable to allocate pty" when sudo is part of a pasted
    multi-line block; the system pty pool can also get exhausted (a
    macOS reboot clears it). expect hits the same wall ("no more ptys").
  - osascript "do shell script ... with administrator privileges" then
    hits TCC: "Operation not permitted" reading ~/Desktop (protected
    location) and writing /dev/rdiskN (removable volume needs Full Disk
    Access; root does not bypass TCC).
* What worked: balenaEtcher (ships with the disk entitlements). Raspberry
  Pi Imager is equivalent.
* Hash gate is mandatory and caught TWO silent "the flash never happened"
  cases this session (the card kept booting the old image). Always
  shasum -a 256 the card's kernel8.img and compare to the source before
  booting. Reference hashes this session:
  - v0.4.98  (old)      52b085df0d906fcf61d6e655ef3e382add0b8c5a42e32c17d8c0c78cc1aa7fae
  - v0.4.134 SMP (hang) 1b8582ae631a57be4b5b8dc3c2d4fd6168272facc007cfcc5c7d989a1fb5e417
  - v0.4.135 6MB rt     b2f7769fd55cdb3d079b8a8b56a1423c6773ed9d5ff1bbed8c559627c60ccfd8
* DONE this session: flash-rpi4.sh now auto-allows a removable Secure
  Digital device (Protocol Secure Digital + Removable + not read-only)
  and adds an explicit --allow-internal override, so the built-in reader
  is usable; and it runs a post-flash kernel8.img hash check that fails
  loudly on mismatch. Live-tested: bash -n + every refusal guard. The
  IS_SD auto-allow and the hash gate exercise only when a card is
  present, so they get their first live run on the next real flash.
