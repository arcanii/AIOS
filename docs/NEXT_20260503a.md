# NEXT 2026-05-03a: COW Step 3 -- wc/shutdown post-promotion EPERM

## Status

v0.4.125 lands all of Step 3's plumbing (parent strip, refcount on
strip, parent fault promotion, fresh-frame tracking, cow_current_cap
helper, fork.c routed through it). Ships with `COW_STRIP_PARENT 0`
because of a residual regression: with the gate on, dash post-promotion
sees EPERM on subsequent fork+exec. With the gate off the system is
v0.4.122-equivalent.

## Repro

```c
// src/process/cow.c
#define COW_STRIP_PARENT 1
```

Build and smoke (`python3 /tmp/aios_drive.py`). Expected:
```
table_size: 64 ...
strip_attempts: 6
strip_errs: 0          <-- mechanism healthy
parent_promotions: 2   <-- promotions actually happen
```
Symptoms in the same smoke session:
* `wc -c /tmp/o` produces no output
* `echo abc | wc -c` produces no output
* `shutdown` prints `dash: 8: shutdown: Operation not permitted`
* dash itself stays alive (REPL works, builtins work, file reads work)

The `Operation not permitted` is `strerror(EPERM)`. dash's
`script:line:cmd: error` format suggests a libc syscall returned -1
with errno=EPERM -- almost certainly fork() or exec() in dash's
job-control path.

## What we know

* The kernel mechanism is correct -- v0.4.123 probe and v0.4.125
  smoke both confirm parent strip + Page_Map remap takes effect with
  no errors.
* Refcount accounting is correct (acquires == releases at idle in
  /proc/cow).
* `cow_current_cap` returns the right cap for promoted vaddrs --
  byte-copy via fork_copy_into_existing produces identical bytes
  whether strip is on or off (eyeball-verified by reading /etc/passwd
  through cat under both modes).
* dash's first fork+exec after a promotion succeeds (the smoke shows
  `ls > /tmp/o` runs and the file gets written; the wc that reads
  it back is what fails).

So the bug is on the *second* fork+exec from a promoted parent, even
though the data copied to the child is byte-correct. That's why
"investigate `do_fork`'s -1 paths post-promotion" is the right
starting point: the bug is in *something we do during fork* that
fails because of state divergence somewhere we haven't traced.

## Investigation plan

1. **Identify the failing -1 path.** Add a `printf` to each of
   `do_fork`'s 12 `return -1` sites with a unique tag. Repro with
   strip on. The tag from the first failure post-promotion identifies
   which step is broken.

   Likely candidates (by gut feeling):
   * cap-slot allocation around minted fault EP -- `vka_cspace_alloc_path`
     for `pfe_dest`
   * cspace cap copying loop -- `seL4_CNode_Copy` for parent's
     ser/fs/exec/auth/pipe slots into child
   * pipe_ep re-mint with child's badge

2. **If do_fork succeeds, look at PIPE_EXEC.** The exec might be
   what fails. PIPE_EXEC unmaps the child's vspace and loads a fresh
   ELF. If parent's vspace tracking is broken in some way that bleeds
   into child setup, the exec might error.

3. **Check the cap rights flow.** `cow_current_cap` returns
   `cow_promoted_global[i].cptr` which was returned by
   `vka_alloc_frame`. That cap has full rights (Read+Write+Grant?).
   When fork.c dups it via `seL4_CNode_Copy(... seL4_AllRights)`,
   the result inherits those rights. Map in root R/W to read bytes.
   Should work, but worth verifying the rights actually match what
   the existing parent_cap path uses.

4. **Sanity-check that nothing free-after-uses parent_cap.** After
   strip + promotion, parent's vspace_t still tracks parent_cap.
   If anything in fork.c (or downstream) calls
   `vspace_unmap_pages(parent_vs, page_va, ..., &vka)` on a
   promoted page, it would delete parent_cap and free its UT --
   children with R/O dups would dangle. Check that no such call
   path exists. (cow_release_proc has the guard already; verify
   no other site.)

## What's NOT the bug

* TLB consistency -- kernel invalidates on Page_Map.
* Refcount drift -- /proc/cow shows balanced counts.
* BSS layout -- per-proc Step 3 state is in cow.c globals (lesson
  from v0.4.124's first BSS-shift breakage).
* Kernel rejection of the strip -- `strip_errs` stays 0.

## How to ship

Once the failing -1 path is identified and fixed:
1. Smoke confirms `wc -c /tmp/o` and `shutdown` work with strip on.
2. Flip `COW_STRIP_PARENT` to 1 in cow.c.
3. Update HANDOVER's "What works" list to include parent COW under
   strip-on behavior.
4. Bump version, commit.

Estimated cost: one focused session. Probably ~30 LOC of fix on top
of the diagnostic.
