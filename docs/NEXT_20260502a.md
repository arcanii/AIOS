# NEXT 2026-05-02a: Root cause of "BSS layout sensitivity"

## TL;DR

**Not a BSS-init bug.** Not seL4, not the elfloader, not the kernel.

`boot_dtb_init()` declared `char dtb_buf[65536]` on the stack. The
user-task root stack is **16 KB** (`CONFIG_SEL4RUNTIME_ROOT_STACK`), so
that 64 KB local array overflowed by 48 KB into BSS, silently
clobbering whichever globals happened to live in the overflow zone
just below `__stack_base`.

For most BSS layouts the clobbered globals were unused gap (or
later-touched scratch buffers), and the bug was invisible. For the
v0.4.115-with-FILEHITS-128/96 layout, `probe_info` / `probe_done`
landed in the overflow zone and got overwritten with the DTB bytes
the buffer was asked to hold. After that, `plat_virtio_probe()` saw
`probe_done != 0` and exited early, and `plat_blk_init()` read garbage
out of the still-uninitialized `probe_info.num_blk`.

Fix: one-liner — make `dtb_buf` `static` so it lives in BSS at a
fixed address, not on the stack.

```c
/* src/boot/boot_dtb.c */
- char dtb_buf[65536];
+ static char dtb_buf[65536];
```

## How the bug presented

* `[plat] Virtio probe: ...` line missing from boot log (probe_done
  was already non-zero, so `plat_virtio_probe` early-returned).
* `[INF] blk: Found block device count=1834970985` — junk pulled out
  of un-zeroed `probe_info.num_blk`. The "junk" was deterministic
  across boots — exactly the bytes of a virtio_mmio DTB node, because
  the same code path keeps writing the same DTB content into the same
  BSS region every boot.
* Fault: `plat_blk_init` then iterates 0x6D5C6DA9 fake devices and
  faults at the first sector read.

## How we found it

1. **Reproduce.** Bumped `FILEHITS_MAX/PATH_MAX` from 96/80 to 128/96
   in [include/aios/filehits.h](include/aios/filehits.h) — `entries[]`
   grows by ~5 KB, which shifts `probe_info` from VA `0x2e93860` to
   `0x2e94d60`. Boot reproduces the bug.

2. **Confirm BSS contents.** Added a scan from `__bss_start__` to
   `__bss_end__` looking for the FDT magic `0xd00dfeed`. One hit at
   user VA `0x2e93d50`, with the next 9 words matching the CPIO
   DTB header byte-for-byte (`totalsize = 0x20aa`, `off_dt_strings
   = 0x1e9c`, etc.).

3. **Connect the dots.** `0x2e93d50` is the address `dtb_buf` would
   land at on the stack:
   * `__stack_top = 0x2eb4000`, `__stack_base = 0x2eb0000` (16 KB).
   * Wait — `__stack_base = 0x2ea0000` for the broken layout,
     `__stack_top = 0x2ea4000`. So sp starts ~`0x2ea4000` and the
     64 KB local pushes sp to ~`0x2e94000`. Add the 16-byte seL4
     extended-bootinfo header (`fdt = dtb_buf + 16`), and the FDT
     magic ends up at `0x2e94000 - 0x10 + small_offset = 0x2e93d50`.
     The arithmetic matches exactly.
   * `probe_info` at `0x2e94d60` is at `dtb_buf + 0x1010`.
     `0x1010` is *exactly* the offset of the
     `"virtio,mmio\0\0\0\0\x02\0\0\0\x01virtio_mmio@a003c00\0"`
     string in the CPIO DTB. The "0x6D5C6DA9" garbage in `num_blk`
     was simply 4 ASCII bytes from inside that DTB string blob.

4. **Verify the diagnosis.** Replacing the 64 KB stack array with a
   `static` BSS array makes the bug disappear regardless of
   `FILEHITS_*` values. With `static`, `probe_info` is no longer
   in any function's stack frame, so it can't be clobbered.

## Why it looked like seL4 / elfloader

The CPIO DTB content was sitting at *user image PA*, which made it
look like the elfloader's memset hadn't zeroed the BSS (or the
kernel had reserved memory weirdly, or the dcache had stale entries
from QEMU). All of those theories were ruled out by:

* Reading `probe_info` at the *very start* of `main()` — every byte
  was zero. The corruption appears later, between `main()` start
  and `plat_blk_init`.
* `boot_dtb_init` is the first thing on that path that touches a
  big buffer. Once you check the address arithmetic, the
  whole thing falls out.

It's a classic stack overflow that masquerades as a memory-init bug
because the overrun *target* (BSS) holds globals that look "always
should be zero" to a reader.

## Files changed

* [src/boot/boot_dtb.c](src/boot/boot_dtb.c): `static char dtb_buf[65536]`,
  comment explaining why.
* [include/aios/filehits.h](include/aios/filehits.h): removed the
  cargo-cult NOTE about "BSS-layout-sensitive bug" since the cause
  is now fixed and the workaround is no longer needed.

## Defense-in-depth recommendations (not done)

These are worth considering separately:

1. **Audit other large stack locals in root-task code.** The next
   biggest is `char tmp[8192]` in
   [src/boot/boot_warmup.c:56](src/boot/boot_warmup.c:56) — uses
   ~50% of the 16 KB stack. Probably fine in practice, but
   ergonomically risky.

2. **Bump `CONFIG_SEL4RUNTIME_ROOT_STACK`.** It's currently 16 KB
   (`build-04/projects/sel4runtime/gen_config/sel4runtime/gen_config.h`).
   Raising to 64 KB or 128 KB gives a much bigger margin against
   future stack-blowing locals. The cost is just a few extra BSS
   pages. Set via `-DSEL4RUNTIME_ROOT_STACK=131072` at CMake time
   (or in `settings.cmake`).

3. **Compile root-task code with `-Wstack-usage=4096`** (or so).
   GCC will warn at compile time on any function that pushes more
   than 4 KB. That would have caught `boot_dtb_init` immediately.

4. **Consider `-fstack-protector-strong`** for the root task. It
   wouldn't have flagged this specific case (the overrun was a
   plain large local, not a write-past-buffer-end), but it's
   cheap insurance against the more common form.

## Verification

* `FILEHITS_MAX/PATH_MAX = 128/96` (the previously-broken layout):
  boots clean, `[plat] Virtio probe: 2 blk, net=no`,
  `Found 2 block device(s)`, login prompt appears. ✓
* `FILEHITS_MAX/PATH_MAX = 96/80` (current values, restored): same
  clean boot. ✓
* No regressions through the boot chain — log drive mount, warmup
  prefetch, getty, all work normally.
