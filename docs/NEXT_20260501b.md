## The blocker

Enabling `cow_setup_segment(child_idx, parent_vs, cp, base, np_cow)`
in `do_fork()` causes the following symptom in OTHER, unrelated
processes spawned via PIPE_EXEC after the fork:

```
sel4utils_new_pages_at_vaddr@vspace.c:492
    Range for vaddr 0xXXXXXX with 1 4k pages not reserved!
[ERR] pipe: BSS fault: map failed err=18446744073709551615
```

`check_reservation` fails on `is_reserved_range` even though the
`bss_reservation` handle is valid (logged: bss_reservation pointer,
start, end all match what was set in the BSS unmap+reserve sequence
in `pipe_server.c` line 818-844).

### Root cause hypothesis

`cow_setup_segment` calls `vspace_reserve_range_at` for the data
portion, which OVERLAPS the existing elf_load reservation that
covers the entire writable segment.

In `deps/seL4_libs/libsel4utils/include/sel4utils/vspace_internal.h`
line 67, `reserve_entries_bottom` returns -1 if it encounters an
already-RESERVED entry. `perform_reservation` in
`deps/seL4_libs/libsel4utils/src/vspace/vspace.c` line 136 has an
`assert` on this error which silently passes in release builds.

The reservation_t is still allocated and inserted into
`data->reservation_head`, but the entries were not actually marked
RESERVED by the new reservation (they were already RESERVED by
elf_load).

When the destroy path runs (`sel4utils_destroy_process` ->
`vspace_tear_down`), `sel4utils_free_reservation` calls
`clear_entries_range(only_reserved=true)` for each reservation.
At line 144 of vspace_internal.h, hitting a POPULATED entry returns
-1 mid-walk. Some entries get cleared; the rest remain.

This leaves the vspace data structure in an inconsistent state
which apparently leaks into the *new* vspace allocated for the
post-exec process. The exact mechanism of the leak across vspaces
is the part I have not nailed down -- vspaces are independent, and
both the cnode and pd are freed and re-allocated, so the corruption
should not transfer. But empirically it does (the BSS reservation
on the new ls process fails its `is_reserved_range` check).

### Things I tried that did NOT fix it

1. `vspace_free_reservation_by_vaddr` before `vspace_reserve_range_at`
   to free the elf_load reservation first -- crashes because
   `find_reserve` returns NULL for the data segment vaddr (the
   elf_load reservation does not cover the *exact* base we pass; or
   the find_reserve lookup is failing for some other reason).

2. Bounding the COW range to the file-backed data portion only
   (using new `filesz` field) -- still triggers the issue, just
   with a smaller overlap.

3. Skipping the R/O sharing step (only doing unmap + reserve) --
   breaks the system entirely because child has no data segment
   and the COW fault handler with no source page fills with zeros,
   destroying parent's initialized data.

### Suggested approaches for the next session

1. **Use the existing elf_load reservation directly.** Instead of
   creating a new reservation, find the existing one and pass its
   handle to `vspace_map_pages_at_vaddr`. Requires either exposing
   `find_reserve` from sel4utils (small patch to dep) or walking
   `data->reservation_head` ourselves via `get_alloc_data`. The
   reservation rights from elf_load are already R/W (PT_LOAD with
   W flag), which is what we want for future R/W remap on write
   fault.

2. **Clone-then-modify approach.** Use
   `sel4utils_bootstrap_clone_into_vspace` as inspiration: walk the
   parent's vspace, for each writable page get the cap, dup R/O,
   and call `seL4_ARM_Page_Map` directly (bypass
   `vspace_map_pages_at_vaddr`'s reservation requirement). Then
   manually update child's vspace data structure via internal
   helpers (`update_entries`). Higher risk of internal mismatch.

3. **Custom vspace.** Replace child's vspace with a custom one
   that tracks COW state natively. Heaviest lift but cleanest.

4. **Workaround: free the elf_load reservation first by walking
   reservation_head ourselves.** We have access to internal headers
   (`sel4utils/vspace_internal.h`). We can walk
   `get_alloc_data(vspace)->reservation_head` and free the
   reservation that contains `base`. Then create our new one
   without overlap.

Approach 4 is probably the cleanest path forward. The main risk is
that elf_load's reservation might be a single big one covering all
LOAD segments, in which case freeing it would orphan the .text
segment too. Need to check.

## How to re-enable

Remove the `(void)cow_setup_segment;` line in
`src/process/fork.c` step 6 and replace the eager-copy loop with
the original COW + eager-BSS hybrid:

```c
cow_clear_proc(child_idx);
for (int s = 0; s < parent->num_segs; s++) {
    elf_seg_info_t *seg = &parent->segs[s];
    if (!(seg->flags & 2)) continue;
    uintptr_t base = seg->vaddr & ~((uintptr_t)PAGE_SIZE - 1);
    uintptr_t data_end = seg->vaddr + seg->filesz;
    uintptr_t cow_end = (data_end + PAGE_SIZE - 1) & ~((uintptr_t)PAGE_SIZE - 1);
    int np_cow = (int)((cow_end - base) / PAGE_SIZE);
    uintptr_t mem_end = seg->vaddr + seg->memsz;
    int np_mem = (int)((mem_end - base + PAGE_SIZE - 1) / PAGE_SIZE);
    int cow_ok = -1;
    if (np_cow > 0)
        cow_ok = cow_setup_segment(child_idx, &parent->proc.vspace,
                                    cp, base, np_cow);
    if (cow_ok < 0) {
        for (int pi = 0; pi < np_mem; pi++)
            fork_copy_into_existing(&parent->proc.vspace, &cp->vspace,
                                    base + (uintptr_t)pi * PAGE_SIZE);
    } else {
        for (int pi = np_cow; pi < np_mem; pi++)
            fork_copy_into_existing(&parent->proc.vspace, &cp->vspace,
                                    base + (uintptr_t)pi * PAGE_SIZE);
    }
}
```

Then verify fix by booting and running `ls /bin | head -5`. Should
see no `BSS fault: map failed` messages.
