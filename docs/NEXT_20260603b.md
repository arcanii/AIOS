* **v0.4.143** (`146d201`) -- the cat|wc / ls|wc = 0 bug is FIXED. Root cause was
  NOT demand-BSS (the docs mis-attributed it): a pipe writer/reader **EOF-ordering
  race**. The creating shell closes its own CREATE write-end ref first (and the
  sibling reader + the writer's own redundant original-write-fd close do the same)
  BEFORE the writer registers, and the old code latched `write_closed` at those
  closes -> premature reader EOF. Fix: `write_closed` is now set in exactly ONE
  place -- `handle_child_fault` when the REGISTERED writer (stdout_pipe_id==pi)
  exits and no other live writer remains (helper `pipe_live_writer_exists`). No
  close latches anymore. Builtins register via dup2/PIPE_SET_PIPES and latch on
  exit too. Timing-independent. VERIFIED deterministic on QEMU --smp 4 AND on the
  **real RPi4 single-core hardware** (cat|wc=2, ls|wc=104, seq 2000|wc=2000,
  multi-stage, early-exit reader).

## Item 1 (harden pipes under load) -- INVESTIGATED, then SCOPED OUT for now

Conclusion: it is a **resource-ceiling project**, and the failures are largely
artifacts of artificial multi-QEMU host-CPU contention. Findings:

* Ceiling: `MAX_ACTIVE_PROCS = 16` (root_shared.h -- BSS-shift hazard to change),
  VKA pool = 8000 pages, morecore = 6 MB/proc (settings.cmake) -> **~16 concurrent
  procs max**.
* Under heavy concurrency the failures CASCADE: VKA/slot pressure -> PIPE_EXEC /
  do_fork fail (EPERM / "Cannot fork") -> a reader that fails to exec leaves the
  writer with no reader -> the writer's bytes are dropped (proved with a PIPE_WRITE
  `written<wlen` "DIAG DROP got=0" probe) -> partial/empty output. 3+ simultaneous
  QEMU boots also overwhelm the host -> boot failures.
* A real pipe-write **data-loss** bug exists (client advances `sent += chunk`,
  ignoring the server's actual `written`; the 4096 ring drops overflow when the
  reader lags -- posix_file.c / aios_posix.c / writev / aios_stdio_write, plus
  PIPE_WRITE/PIPE_WRITE_SHM server side). It is SECONDARY (mostly triggered by the
  absent/slow readers above). A client busy-yield fix (v0.4.144 attempt) was
  REVERTED: honoring `written` means retry-until-drained, which busy-spins on a
  full ring and ADDS pressure (made 2-concurrent flake where it had been clean) and
  deadlocks when a reader spawns late behind a blocked writer ("Cannot fork"). The
  only non-harmful fix is server-side NON-spinning writer-blocking (mirror the
  reader-blocking machinery: pipe_read_blocked -> pipe_write_blocked, stash +
  resume on drain, EPIPE on read_closed) -- but it does NOT fix the load flakes
  (the resource ceiling) and keeps a blocked writer alive longer.
* CRUCIAL: single-instance QEMU and the **real RPi4 hardware work reliably**. The
  load flakes need 2-3 concurrent QEMU (host-CPU starvation), not normal use.

So item 1 was deferred (no v0.4.144 fix landed; the bump was reverted). The deep
capacity/admission work is large and largely unjustified for real use.
